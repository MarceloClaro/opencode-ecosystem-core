# SPEC-935-R607 — Otimização e limites da LLM local no host i5-1035G1

**Status:** concluída (medição + configuração). Resultado negativo quanto a
aproximar o `big-pickle` — ver "Veredito".

## 1. Escopo

Otimizar o desempenho da LLM local servida por Ollama usada pelo OpenCode, e
avaliar se é possível aproximá-la do `opencode/big-pickle` neste hardware.

## 2. Ambiente medido

| Item | Valor |
|---|---|
| CPU | Intel Core i5-1035G1, 4 núcleos / 8 threads, AVX-512 + VNNI |
| RAM | 11.843 MB |
| Swap | 23.072 MB |
| GPU | nenhuma (CPU-only) |
| Ollama | 0.31.1 |

## 3. Metodologia e correção de métricas

Duas suítes determinísticas, `temp=0.1`, gabaritos exatos e checagem por
execução de código:

- **Tier fácil (13 tarefas)**: factual, aritmética, instrução, código simples.
- **Tier difícil (11 tarefas)**: raciocínio multi-passo com distrator, código
  executado, restrição negativa, recuperação em contexto longo.

Duas correções de harness foram necessárias e são parte do resultado:

1. `list3` nunca funcionou: `_norm` removia as vírgulas **antes** do split, logo
   `parts` sempre tinha 1 elemento e a tarefa falhava para todos os modelos.
2. O `tps_med` do sweep era a mediana do tok/s por tarefa, mas tarefas factuais
   têm respostas de 1–2 tokens. Medir 2 tokens em ~1 ms produz leituras sem
   sentido que **inflaram a mediana de 11,28 para 16,20 tok/s**. Throughput foi
   remedido com prompt fixo + `num_predict=128` fixo + mediana de 3 runs.

Consequência: as afirmações anteriores de "16,20 tok/s com num_kv=8" e de
"num_kv é o melhor ajuste" eram **artefatos de medição** e estão revogadas.

## 4. Qualidade (tier difícil, 11 tarefas)

| Modelo | acertos | acc |
|---|---|---|
| `opencode/big-pickle` (cloud) | 8/11 | 0,727 |
| `gemma4:e4b-it-qat` | 7/11 | 0,636 |
| `gemma4:e2b-it-qat` | 7/11 | 0,636 |
| `qwen3:8b` | 7/11 | 0,636 |
| `qwen3:14b` | 7/11 | 0,636 |

No tier fácil, e4b fez 13/13 e e2b 11/13. A diferença entre 7/11 e 8/11 (uma
tarefa) **não é significativa** com n=11. `qwen3:14b` (9,3 GB) não trouxe ganho
de qualidade e consumiu a RAM (disponível caiu a 449 MB).

## 5. Throughput (128 tokens, mediana de 3 runs)

| Configuração | tok/s |
|---|---|
| e2b `num_thread=4` `num_ctx=4096` | **7,90** |
| e2b `num_thread=4` `num_ctx=2048` | 7,63 |
| e2b `num_thread=2` `num_ctx=4096` | 6,34 |
| e2b `num_thread=4` `num_ctx=4096` `num_kv=8` | 6,54 |
| e2b `num_thread=4` `num_ctx=4096` `num_kv=16` | 6,17 |
| e2b `num_thread=4` `num_ctx=8192` `num_kv=8` | 5,46 |
| e2b `num_thread=8` `num_ctx=8192` | 1,76 |
| e4b `num_thread=4` `num_ctx=4096` | 3,04 |
| e4b `num_thread=4` `num_ctx=8192` | 2,89 |
| e4b `num_thread=8` `num_ctx=8192` | **0,19** |

Conclusões sustentadas por efeito grande (a variância entre runs é ~1,8×):

- `num_thread=4` é o ótimo; `8` é catastrófico (threading excessivo em 4 núcleos).
- `num_ctx` menor é mais rápido; 4096 > 8192 > 24576.
- `num_kv` 8/16 **não** ajuda de forma confiável.
- `think: true` no e4b piora a acurácia (0,867 → 0,667 no tier fácil) e a
  velocidade (5,47 tok/s). Mantido desligado.
- Flash attention no prefill: 27,7 → 29,3 tok/s, dentro do ruído. Removido.

## 6. O gargalo real: prefill de contexto longo + catalogo de agentes

### 6.1 Medicao isolada (via /api/chat, sem opencode)

| Prompt | `num_ctx` | Prefill |
|---|---|---|
| ~1k | 4096 | 31,1 tok/s |
| ~4k | 6144 | 27,9 tok/s |
| ~8k | 10240 | 24,6 tok/s |
| ~15k | 16384 | 21,3 tok/s |
| ~21k | 24576 | 21,6 tok/s (675 s) |

### 6.2 Medicao de ponta a ponta (`opencode run`)

O log do ollama (task.n_tokens) revela a causa real da lentidao:

| Perfil | Tamanho do prompt | Tempo por turno | Erros |
|---|---|---|---|
| completo (216 agentes, 105.932 B) | **21.136 tokens** | 6m09s / 8m40s / **18m00s** | 500 (timeout 5 min) |
| minimo (1 agente, 689 B) | **2.051–6.712 tokens** | 1m32s / 2m04s / 5m01s | nenhum |

O vazamento de 21.136 tokens vem do catalogo de 216 agentes do opencode.json.
Cortar os agentes reduz o prompt ~10x e o turno de ~6-18 min para ~1,5-5 min.
O turno de 18 min foi causado por: timeout de 5 min no endpoint /v1 do ollama
(gerou 500), cancelamento e re-tentativa; no retry, 20.112 tokens vieram do
prompt cache e so ~1.024 precisaram de prefill.

O perfil minimo vive em `opencode.local.jsonc` (usar com
`OPENCODE_CONFIG=opencode.local.jsonc opencode`). Modelos `*-tuned` com
`num_thread=4` e `num_ctx=24576` via Modelfile.

## 7. Configuração aplicada

- Modelos `gemma4:e4b-tuned` e `gemma4:e2b-tuned` (Modelfile com
  `num_thread=4`, `num_ctx=24576`), criados via `ollama create`. O Modelfile é
  o único canal confiável: não existe `OLLAMA_NUM_THREADS`, e
  `num_kv`/`kv_cache_type` não são aceitos como PARAMETER.
- `integrations/opencode_cli.py`: `limit.context` corrigido de 32768 para
  **24576** (32768 nunca coube em 11,8 GB), `output` 4096 → 2048, e as tags
  `*-tuned` registradas. `reasoning_effort: none` mantido.
- `opencode.local.jsonc`: **perfil mínimo com 1 agente** para a LLM local,
  usado via `OPENCODE_CONFIG=opencode.local.jsonc opencode`. É o artefato que
  de fato viabiliza o uso local (prompt ~2-7k tokens contra 21k do perfil
  completo).
- `/etc/systemd/system/ollama.service.d/10-perf.conf`: apenas
  `OLLAMA_KEEP_ALIVE=30m` (evita recarregar 6–10 s por request) e
  `OLLAMA_MAX_LOADED_MODELS=1` (impede dois modelos residentes e OOM em 11,8 GB).
- `OLLAMA_KV_CACHE_TYPE=q8_0` e `OLLAMA_FLASH_ATTENTION=1` foram testados e
  **removidos**: sem ganho mensurável.

## 8. Veredito

**Não é possível aproximar o `big-pickle` para uso agentivo no perfil completo**
(216 agentes): o prompt de 21k tokens custa 6–18 min por turno e esbarra no
timeout de 5 min do endpoint /v1. Além disso, todas as alternativas locais
testadas (e2b, e4b, qwen3 8b, qwen3 14b) empatam em qualidade no tier difícil,
e o e4b entrega a mesma qualidade a 2,6× a latência do e2b.

O caminho pratico:

- **LLM local, perfil mínimo** (`opencode.local.jsonc`): viável para tarefas
  diretas. Prompt ~2-7k tokens, ~1,5–5 min por turno, sem reinicios 500.
  `gemma4:e2b-tuned` é o recomendado (velocidade); `gemma4:e4b-tuned` quando
  qualidade > latência.
- **Modelo cloud** (`big-pickle`, 8/11 no tier difícil) para o loop agentivo
  completo com o catálogo de 216 agentes, onde o prompt grande é inviável
  localmente.
- Escalar modelo local (14B) não resolve: o custo domina pelo prefill no
  prompt longo, não pelo tamanho do modelo nesta classe.

## 9. Restrições / anti-overclaim

- Diferenças de 1 tarefa em n=11 não sustentam alegação de superioridade.
- Throughput tem variância de ~1,8× entre runs; só efeitos ≥2× foram tratados
  como conclusivos.
- A LiteRT-LM permanece inviável como modelo primário (SPEC-935-R606):
  contexto 20480 rejeita o prompt de 21k e 32768 causa OOM-kill.

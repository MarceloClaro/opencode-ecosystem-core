# R890 — Curadoria de integrações locais, grupo C

**Consulta: 14 de outubro de 2026. Método: leitura dirigida de fontes primárias fixadas e inspeção estática REA.** Não foram instalados nem iniciados TorBot, LiteRT, MCP Server.exe, WhatsApp ou Toolbox. Nenhuma conta, mensagem, crawler, modelo ou executável desses projetos foi acionado. A inspeção REA utilizou o runtime que já existia no Core.

O maior aproveitamento imediato deste grupo é **um padrão de configuração explícita de ferramentas e efeitos**, sem acrescentar outro coordenador ao ecossistema. Toolbox oferece referências úteis para ferramentas nomeadas e parâmetros; MCP Server.exe e WhatsApp mostram por que o Core deve avaliar transporte, destino e efeitos antes de ativar uma integração. LiteRT contribui para uma futura extensão de visão local em dispositivos. TorBot pertence a um fluxo separado de coleta de rede.

## 1. TorBot: coleta de rede separada da compreensão local

O manifest declara `torbot` **4.1.0**, Python `>=3.7`, HTTPX/SOCKS, BeautifulSoup, igraph, NumPy, SciPy e scikit-learn. Há versões diferentes entre `pyproject.toml` e `requirements.txt`, inclusive NumPy, HTTPX e SciPy; compatibilidade com Python 3.14 não foi demonstrada. A entrada é `main.py`, que recebe URL e profundidade, usa proxy SOCKS5 e pode dispensá-lo por opção explícita. [Manifest](https://github.com/MarceloClaro/TorBot/blob/abb44f69d44d59bbf53301911e860e2f15440cb9/pyproject.toml), [requisitos](https://github.com/MarceloClaro/TorBot/blob/abb44f69d44d59bbf53301911e860e2f15440cb9/requirements.txt), [entrada](https://github.com/MarceloClaro/TorBot/blob/abb44f69d44d59bbf53301911e860e2f15440cb9/main.py).

A operação normal consulta `check.torproject.org` para exibir o IP quando não está em modo silencioso. O atualizador pode iniciar Git e fazer `git pull`. Essas são operações de rede e escrita, distintas de ler um artefato local. A contribuição aproveitável é o formato de árvore de links e a separação entre coleta e apresentação. Um eventual especialista precisaria receber do primário destinos e orçamento explícitos, guardar a procedência e devolver dados ao MetaBus; não deve ser ativado como dependência do raciocínio local. [Consulta externa](https://github.com/MarceloClaro/TorBot/blob/abb44f69d44d59bbf53301911e860e2f15440cb9/src/torbot/modules/api.py#L15), [atualizador](https://github.com/MarceloClaro/TorBot/blob/abb44f69d44d59bbf53301911e860e2f15440cb9/src/torbot/modules/updater.py).

O arquivo de licença contém GPL versão 3, enquanto a classificação automática da API é inconclusiva. A avaliação não fixa uma variante SPDX `only`/`or-later` nem copia código desse projeto. [Licença lida](https://github.com/MarceloClaro/TorBot/blob/abb44f69d44d59bbf53301911e860e2f15440cb9/LICENSE.md).

## 2. LiteRT samples: visão em dispositivos, com preparação de modelos

A amostra examinada é segmentação de imagens Android, com CPU/GPU e outra variante NPU. Ela não é um substituto direto do backend LiteRT-LM do Core no WSL. O catálogo Gradle fixa LiteRT **2.0.3**, Kotlin **2.1.0** e Android Gradle Plugin **8.10.0**; o README da segmentação ainda menciona `2.0.0-alpha`. Na versão CPU/GPU lida, `minSdk=23`, `compileSdk=34` e ABIs ARM. Esses requisitos não demonstram execução no computador atual. [Catálogo de versões](https://github.com/MarceloClaro/litert-samples/blob/d7939f4f8720ed444afc2078674560dfac09b259/v2/image_segmentation/kotlin_cpu_gpu/android/gradle/libs.versions.toml), [build Android](https://github.com/MarceloClaro/litert-samples/blob/d7939f4f8720ed444afc2078674560dfac09b259/v2/image_segmentation/kotlin_cpu_gpu/android/app/build.gradle.kts).

Há uma tarefa de download de `selfie_multiclass.tflite` no Hugging Face ligada a `preBuild`; ela não foi executada. Preparar a amostra pode acessar rede, mesmo que a inferência posterior aconteça no dispositivo. Os números de desempenho de telefone publicados pelo projeto não foram reproduzidos e não são resultados do Core. [Download automático do build](https://github.com/MarceloClaro/litert-samples/blob/d7939f4f8720ed444afc2078674560dfac09b259/v2/image_segmentation/kotlin_cpu_gpu/android/app/download_model.gradle), [escopo das amostras](https://github.com/MarceloClaro/litert-samples/blob/d7939f4f8720ed444afc2078674560dfac09b259/v2/image_segmentation/README.md).

Contribuição possível: um futuro especialista de visão que declare tarefa, modelo/hash, entrada, saída, dispositivo e backend realmente utilizado. Preparação de pesos deve ser explícita, seguida por teste de inferência local. Essa extensão fica fora da implementação desta curadoria.

## 3. MCP Server.exe: aproveitar contratos, evitar novo roteador

O pacote `mcp_exe` **0.12.0** oferece CLI `bin/cli.js`, biblioteca TypeScript, composição de servidores e transportes SSE/stdio/WebSocket. O empacotamento configurado usa `pkg` com Node **18**, Windows e macOS; não há prova de um executável Linux compatível nem de benefício sobre o `ecosystem-network` já existente. Dependências incluem MCP SDK `^1.12.1`, Express, WebSocket, Zod e ferramentas de notificação. [Manifest](https://github.com/MarceloClaro/mcp_server_exe/blob/ad5555bc090813f26bdc9fdf402e7d517102de2b/package.json), [entrada CLI](https://github.com/MarceloClaro/mcp_server_exe/blob/ad5555bc090813f26bdc9fdf402e7d517102de2b/bin/cli.js).

No caminho lido, o transporte SSE é padrão; a interface usa `0.0.0.0` quando não há host específico e há configuração CORS com origem `*`. Configuração JavaScript customizada passa por `require`, e servidores stdio declarados no arquivo de composição tornam-se processos filhos. Não é uma configuração passiva de dados. Não foi encontrado um gate de autorização do Core nesses caminhos externos; isso é limite da amostragem, não auditoria completa de segurança. [Inicialização](https://github.com/MarceloClaro/mcp_server_exe/blob/ad5555bc090813f26bdc9fdf402e7d517102de2b/src/server.ts#L155), [CORS/interface](https://github.com/MarceloClaro/mcp_server_exe/blob/ad5555bc090813f26bdc9fdf402e7d517102de2b/src/mcpRouterServer.ts#L90), [composição](https://github.com/MarceloClaro/mcp_server_exe/blob/ad5555bc090813f26bdc9fdf402e7d517102de2b/src/serverComposer.ts#L150).

O Core pode aproveitar a ideia de ferramentas agrupadas e um recibo de transporte. A adoção integral duplicaria composição e aumentaria a superfície de execução. A sugestão é manter o primário e sua configuração canônica, exigir transporte/destino explícitos e tratar qualquer arquivo `.js` de configuração como código executável.

## 4. WhatsApp MCP: aplicação conectada a uma conta pessoal

A arquitetura separa uma ponte Go/Whatsmeow e um servidor FastMCP Python stdio. O projeto Python é **0.1.0**, requer Python `>=3.11`, HTTPX, Requests e MCP; a ponte fixa Go **1.24.1** e `go-sqlite3`, que necessita CGo. O cliente realiza conexão com WhatsApp e autenticação por QR, persistindo sessão e mensagens em SQLite. [Manifest Go](https://github.com/MarceloClaro/whatsapp-mcp/blob/7d6a06dcdce1f01dfb24f60e1030d5efba9f3b88/whatsapp-bridge/go.mod), [manifest Python](https://github.com/MarceloClaro/whatsapp-mcp/blob/7d6a06dcdce1f01dfb24f60e1030d5efba9f3b88/whatsapp-mcp-server/pyproject.toml), [conexão](https://github.com/MarceloClaro/whatsapp-mcp/blob/7d6a06dcdce1f01dfb24f60e1030d5efba9f3b88/whatsapp-bridge/main.go#L803).

O MCP expõe leitura de mensagens e contatos, mas também envio de mensagens, arquivos e áudio, além de download de mídia. A ponte REST usa endereço `:8080`; os handlers examinados validam método e corpo, sem uma checagem de autenticação nesse trecho. A URL Python `localhost:8080` não restringe a interface em que o servidor Go escuta. [Ferramentas MCP](https://github.com/MarceloClaro/whatsapp-mcp/blob/7d6a06dcdce1f01dfb24f60e1030d5efba9f3b88/whatsapp-mcp-server/main.py#L157), [handlers e interface](https://github.com/MarceloClaro/whatsapp-mcp/blob/7d6a06dcdce1f01dfb24f60e1030d5efba9f3b88/whatsapp-bridge/main.go#L678).

Armazenamento local não garante que mensagens não cheguem ao LLM: o próprio README explicita o acesso por ferramentas. A recomendação é manter essa integração opcional e desativada nesta etapa. Uma adoção posterior exigiria escopo de conta e dados, redação de informações sensíveis, leitura separada de envio e autorização humana para comunicação. Nenhuma conta foi acessada nesta avaliação. [Modelo de dados declarado](https://github.com/MarceloClaro/whatsapp-mcp/blob/7d6a06dcdce1f01dfb24f60e1030d5efba9f3b88/README.md#L7).

## 5. Toolbox: melhor padrão de dados deste grupo, com limites explícitos

O fork contém o MCP Toolbox for Databases, com fontes, ferramentas e conjuntos de ferramentas declarados. O código fixa Go **1.23.8** e toolchain **1.24.4**, com drivers SQLite/PostgreSQL/Redis e serviços de nuvem. A CLI suporta `--stdio`; o servidor HTTP tem endereço padrão `127.0.0.1:5000`. Exportação de telemetria GCP é `false` por padrão e OTLP usa string vazia; exportadores são criados quando essas opções são configuradas. Isso não audita todas as dependências nem garante ausência de rede. [Manifest](https://github.com/MarceloClaro/genai-toolbox/blob/648eede62b65b4d3d6d1728e726237384df5f32c/go.mod), [flags](https://github.com/MarceloClaro/genai-toolbox/blob/648eede62b65b4d3d6d1728e726237384df5f32c/cmd/root.go#L164), [telemetria](https://github.com/MarceloClaro/genai-toolbox/blob/648eede62b65b4d3d6d1728e726237384df5f32c/internal/telemetry/telemetry.go#L112).

O padrão útil é publicar consultas nomeadas com parâmetros tipados e selecionar somente um toolset. Porém, `sqlite-sql` aceita também escrita e DDL; `templateParameters` altera o texto SQL e a documentação reconhece maior exposição a injeção. A fonte SQLite abre o caminho fornecido, sem impor modo somente leitura. Um banco local não transforma qualquer ferramenta SQL em leitura segura. [Contrato SQL](https://github.com/MarceloClaro/genai-toolbox/blob/648eede62b65b4d3d6d1728e726237384df5f32c/docs/en/resources/tools/sqlite/sqlite-sql.md), [execução](https://github.com/MarceloClaro/genai-toolbox/blob/648eede62b65b4d3d6d1728e726237384df5f32c/internal/tools/sqlitesql/sqlitesql.go#L131), [abertura do banco](https://github.com/MarceloClaro/genai-toolbox/blob/648eede62b65b4d3d6d1728e726237384df5f32c/internal/sources/sqlite/sqlite.go#L92).

Foi observada uma questão adicional no código de `ToolsetConfig.Initialize`: a lista de ponteiros é criada com comprimento igual ao número de ferramentas e depois recebe novos elementos por `append`. Isso deixa posições iniciais nulas nessa lista. O efeito sobre cada consumidor não foi executado; a adoção dessa revisão exigiria um teste específico. Não foi copiada a implementação. [Construção do toolset](https://github.com/MarceloClaro/genai-toolbox/blob/648eede62b65b4d3d6d1728e726237384df5f32c/internal/tools/toolsets.go#L39).

## REA executado e fronteira da evidência

As leituras GitHub ficaram separadas da análise local. A amostra REA foi uma cópia byte a byte de `mcp_server_exe/src/tools/mcpConfig.js` do commit fixado, com **1.834 bytes** e hash `8499acbbe854ab6b7488f389e18fbe4c334852332179605466eff5d5e44b54e6`. Ela foi tratada como texto; o plugin JavaScript não foi importado nem executado.

Foram preservadas duas recusas: a ferramenta de aplicação JavaScript não aceita um arquivo `.js` isolado; a inspeção do diretório com todos os arquivos selecionados excedeu o orçamento MCP de aproximadamente 10 MiB. Uma projeção de um arquivo em diretório próprio concluiu a inspeção pelo primário: **1 arquivo analisado, 227 nós AST visitados e zero falhas de parsing**, em 5,519 s nessa chamada. O Evidence ID é `ev_1cd2e04b8a090bc9c96bfa54b935b0ae063a4360633a255fac64e510cd2576e8`.

Também foi executado `MarceloClaroOrchestrator.rea_assistant_action` nessa projeção: resultado concluído, `target_unchanged=true`, somente interface `lo`, nenhuma rota externa disponível e sonda de conexão ao host sem sucesso. A fronteira declarada é o worker analítico e seus descendentes; não abrange um cliente LLM em nuvem. O recibo local é `outputs/core-r890/c-rea-isolated.json`.

Esses números descrevem somente essa projeção. Não validam o servidor completo, o transporte, o empacotamento ou a autorização das ferramentas. O REA também declara que relações estáticas não demonstram execução e que expressões dinâmicas podem permanecer sem resolução. Os recibos locais preservam as recusas, a chamada direta concluída e a execução pelo assistente isolado; o manifesto desta revisão especifica o resultado de cada uma. Não há promoção de confiança nem validação externa.

## Uma adaptação pequena proposta, ainda não implementada

**Pré-verificação declarativa de integração MCP no validador existente do Core.** Acrescentar a `integrations/mcp_validation.py` um contrato passivo para transporte, comando, raízes, destino, ferramentas permitidas e efeitos declarados. O gerador `integrations/opencode_cli.py` e os adaptadores subordinados a `MarceloClaroOrchestrator` consumiriam o mesmo resultado; não seria criado outro servidor ou coordenador.

O primeiro escopo poderia rejeitar configuração JavaScript executável, comando sem lista explícita de argumentos, ferramenta não declarada, interface pública em um perfil local e destino remoto em um perfil sem rede. Leitura, gravação de cache, escrita de dados e comunicação externa receberiam classificações distintas. Essa classificação não seria aceita como prova do comportamento de um servidor: consultas reais, hashes, isolamento e autorização continuariam necessários.

Critérios propostos: configuração local válida passa sem iniciar processos; `.js`, host público, destino remoto proibido e ferramenta desconhecida falham antes da ativação; o diagnóstico não imprime credenciais; os campos `installation`, `configuration_review`, `authentication` e `completed_operation` permanecem distintos. As referências principais são o padrão de toolsets do Toolbox e os efeitos concretos identificados em MCP Server.exe/WhatsApp. A proposta depende de spec e testes próprios; **nenhuma integração R890 foi instalada ou ativada por este documento**.
